# CR-1: mandatory report source type

`source` prefixes are case-sensitive: `SAT` → `SATELLITE`, `GND` → `GROUND`, `MOB` → `MOBILE`, and every other/null value → `UNKNOWN`. The stored value is mandatory after finalization. Instances are replaced one at a time.

| Stage | Action, lock and verification | Pause/rollback |
|---|---|---|
| 1. Expand | A v1.1 replica applies Flyway V2. Adding a nullable column and the unvalidated check needs brief `ACCESS EXCLUSIVE`; `lock_timeout=2s` aborts instead of waiting behind traffic. The classifier trigger fills writes from both binaries. The check is immediately enforced for new/changed rows. An empty clean install validates and sets NOT NULL immediately. Verify both versions ingest and `source_type` is populated for new rows. | If lock acquisition fails, Flyway rolls back V2 and the v1.0 replica continues. If V2 commits, leave the additive objects: v1.0 remains compatible. Drain and restore the v1.1 replica if application checks fail. |
| 2. Roll code | Drain A, replace it with v1.1, wait for readiness and re-enable it; repeat B. v1.1 responses/filter use `coalesce(source_type,classify_source(source))`, so legacy rows are correct before backfill. The v1.0 web console tolerates the additive field. | Drain and restore either v1.0 image. Do not remove the trigger/column while any v1.1 instance is running. |
| 3. Backfill | `backfill-source-type.sql` scans the report primary key in 5,000-row keyset pages. Each transaction row-locks only its updates and the singleton checkpoint, commits, then sleeps 50 ms. The checkpoint stores the last key and count. Monitor latency, WAL, disk and replication lag; reduce page size/increase pause when service indicators degrade. | Cancel the client at any commit boundary. Completed pages and checkpoint remain; rerunning resumes strictly after the saved key. Only one backfiller should run. |
| 4. Verify/finalize | `verify-source-type.sql` must report zero null and zero misclassified rows. `VALIDATE CONSTRAINT` takes `SHARE UPDATE EXCLUSIVE` while scanning: reads/writes continue, conflicting DDL waits. The validated presence check lets `SET NOT NULL` take only a short `ACCESS EXCLUSIVE` metadata lock; the 2-second timeout makes it retryable. | A timeout leaves commands retryable. Before finalization, rollback is the v1.0 binary sequence. After finalization old binaries still write successfully through the trigger. Relaxing the invariant would require a new forward migration. |

At an effective 5,000 updated rows/s, 500 million rows require about 27.8 hours; at 2,000/s, about 69.4 hours. These are planning estimates, not promises. Measure the first pages, include WAL/replication/autovacuum headroom, schedule whole-table verification off peak, and pause when live request latency or storage pressure breaches the site threshold.

Before finalization, prove: both APIs are v1.1 and healthy; no rollback to code that assumes the column is absent; the trigger is enabled; backfill checkpoint reached the table end; null/misclassification counts are zero; and storage/replicas are healthy.
